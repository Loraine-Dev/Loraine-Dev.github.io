## Trace 找到什么，实际改了什么

另用 CDP 收集可在 DevTools 打开的 Performance Trace：390×844，CPU 4 倍、实际施加网络节流 150 ms / 1.6 Mbps、关闭缓存。该数据与 Lighthouse simulated 不可直接混算。

1. 基线主线程局部 WebGL 提交反复产生约 80–130 ms 长任务；观察窗口约有 55 个此类事件。改为 OffscreenCanvas Worker，图片读取、ImageBitmap 转换、纹理上传与绘制一起离开主线程。只在主线程创建 ImageBitmap 再传递仍产生 148–208 ms 阻塞，已放弃该方案。最终 Trace 主线程未再记录这些 GL 调用；仍有 64 / 60 ms 的其他长任务，不能报告全程零阻塞。GPU 成本并未消失。
2. 首次滚动原来加载约 132 KB 压缩 Three chunk 并初始化相机渲染，曾出现最长约 386 ms 的主线程任务。手机改用同一相机、FOV、平面深度与投影公式的 CSS 合成，按滚动/尺寸变化更新，无闲置循环，滚动新增模块约 1.6 KB。桌面 Three 路径保持原样。四个相同滚动进度的冻结截图与相机数值已保留，未粗暴放大全景。
3. midFog 的 CSS mask 与预加载请求模式不一致，修正 crossorigin，普通缓存浏览器确认 mask 单次请求。Worker 读取原图在普通缓存验证中复用缓存（第二次传输 0 B）；关闭缓存的诊断不能据此假定无第二次网络读取。
4. 原主图、云雾已有可在 HTML 发现的高优先级预加载，主图不是懒加载；没有外部网络字体或 GSAP。首屏未发现加载其他内页艺术资源。原生材质回退改为延迟导入，不随首屏模块执行。
5. 局部水位移桌面 1.6→2.1 / 手机 1.8→2.2，树光增益 0.4→0.6 / 0.44→0.62。光路与云雾增益保持原值。只加强已有局部响应，没有增加特效系统。

### LCP 为什么还慢

最终 Lighthouse 将较大的 cloud-billow 判为 LCP，而非仅主背景图。它依赖云素材解码、遮罩、布局和首轮合成，不能只压主图解决。五轮 Style & Layout 约 878–1092 ms，Other 约 988–1297 ms，脚本执行约 100 ms 级；残余成本更偏向初始样式/遮罩/合成与软件图形环境。Lighthouse 的单项原始 render-delay 与模拟总 LCP 不是同一时间模型，不能直接相加。

实际节流 Trace 中手机主图原始体积 173344 B，下载约 2.36 秒；维持当前美术时它也占据网络预算。下一步若继续压低 LCP，应在真机 GPU 环境确认遮罩/云层合成成本，评估保持透明边缘和细节的云素材编码/绘制范围，以及逐资源优先级。未擅自降低已认可云雾密度、分辨率或延迟它到首屏之后。

## 动态的真实组成与限制

|模块|实际区域与方法|素材与限制|
|---|---|---|
|云雾|原山谷与水岸多层独立云纹理，位移与形变|沿用现有独立云素材/遮罩/配置，未替换|
|丁达尔光|树后到山谷的既有光路范围，两个有地形遮挡的局部光姿态混合，内部枝影条带连续变化|已有独立光路图；是局部 2.5D 重照明，不是真实三维体积光|
|水面|水体遮罩内部，对原画纹理进行两个方向不同的细小折射采样与反射变化|水面烘焙在主图；使用独立无损区域遮罩，没有移动整片水图，也没有独立水模型|
|树冠|亮度筛选的少量枝叶内部，方向性受光窗口缓慢移动，轮廓与树干固定|独立无损区域遮罩；没有拆出的枝叶，没有枝叶摆动|

桌面与手机分别使用专门构图及遮罩。周期在 living-scene.json：光 16 秒、水 7.3 秒；云雾原配置保持。纹理偏移有空间变化，光路和树光有局部受光变化；不把“动画时间前进”或像素差异当作肉眼自然度合格。

开发录屏保留正常速度：桌面/手机各初始化后静置连续 30 秒，完整原片另外保留加载及滚动。另有四项独立 off 3 秒 → on 10 秒 → off 3 秒的对比，时间标记在同名 JSON。没有快放或插帧。录制环境使用软件图形路径，材质帧率上限 6（硬件路径上限桌面 18 / 手机 15）；这不是设备屏幕帧率结论。

静态检查未见明显构图/边缘破坏，水体折射和局部受光仍需用户按正常速度判断是否足够自然、是否在 5–10 秒内成立。30 秒原片供检查循环、重影和闪烁；不自行宣布通过艺术验收。主图中瀑布、叶片与天空受光烘焙在一起；本轮未制作独立瀑布、枝叶摆动或天空动画，也未用统一闪烁冒充。
